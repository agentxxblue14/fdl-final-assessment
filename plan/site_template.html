Part 1: the broken calculator, fixed

Same load, same inputs, from the README: revenue $2,000, 500 miles, $4 fuel, 10 mpg, $400 driver pay, $50 tolls, 10% dispatch, $100 other costs, 20% target margin. The original code made fuel and the dispatch fee 100 times too high, so a profitable load looked like a big loss.

Tests passing

Before: 5 tests, 1 passing, and that one by accident. After: 32 tests, all passing on Python 3.10 to 3.13. Your expected values were not changed.

D1Fuel multiplied miles by mpg instead of dividing: $20,000 instead of $200.
D2Dispatch fee treated 10% as 1000%: $20,000 instead of $200.
D3Margin was measured against cost, not revenue, and crashed on a zero load.
D4Break-even rate ignored the dispatch fee: $750 instead of $833.33.
D5Suggested rate stacked the percentages and gave 18% margin, not 20%.
D6Input checks let 0 mpg, negative costs, text and infinity through.

Root causes, the rounding change and all test evidence: SUBMISSION.md.

Who does what

The owner owns every account and approves every release. The Lead builds the hard and risky parts and reviews all code. The TA works from half-day tickets with acceptance criteria and has no production access.

Nothing reaches production by accident

Protected main branch, automated tests, a human review of every change, and the owner's yes on the release notes. Backups before every database change, and an audit log of who changed what.

The five risks I would watch first

How I would handle them

Outside APIs: discovery starts in phase 3, each integration sits behind one adapter so a provider can be swapped.

Existing Replit project: a phase 0 inventory, shown live, before any estimate is final.

Scope: each phase has a fixed scope; new ideas go to a backlog the owner ranks at milestone reviews.

Data isolation: enforced in the code and in the database, tested on every change, external test before M2.

AI accuracy: measure the straight-through rate from day one and route unsure documents to a review queue.
